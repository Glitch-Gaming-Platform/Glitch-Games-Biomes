# Galois migrations and upgrades

Galois upgrades can cross generated APIs, Node/Python process framing, source dependency tracking, native bindings, binary index formats, published static objects, Bikkie references, browser caches, and packaged runtimes. Classify the compatibility surface before editing.

## Compatibility rules

1. Treat generated TypeScript, Python materializer signatures, and the materializer map as one unit.
2. Preserve dependency ordering and literal meaning in serialized programs unless Node and Python are upgraded atomically.
3. Keep Python serializer tags and TypeScript `AssetDataMap` synchronized.
4. Binary index or tensor format changes require compatible native readers and consumer deployment planning.
5. Published objects are immutable. Publish new bytes under a new content hash.
6. Upload new objects before deploying an index, generated definition, or Bikkie reference that points to them.
7. Keep old static objects available through the rollback and cache-retention window.
8. Increment `ASSET_EXPORTS_SERVER_VERSION` for output-changing player-mesh upgrades.
9. Caches may be invalidated, but disabling or deleting a cache must not change generated bytes.
10. Do not validate an upgrade only against a previously installed Voxeloo extension; test the current native source and bindings.

## Change classification

| Change                                | Main risks                                                                             | Minimum additional validation                                               |
| ------------------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Raw art or audio                      | Unexpected bounds, materials, animation names, duration, size, or license/source drift | Focused export, viewer/runtime inspection, content-hash diff                |
| TypeScript recipe                     | Dependency/order change, missing source tracking, changed logical path                 | DSL tests, Python export, index diff, affected consumer                     |
| DSL type or function                  | Generated API/materializer mismatch and query incompatibility                          | Regeneration, TS graph tests, Python materializer tests                     |
| Python materializer or serializer     | Different bytes, uncaught errors, stale incremental cache, platform differences        | Python suite, clean versus incremental comparison, representative export    |
| Voxeloo Galois native code            | ABI/binding drift, tensor layout, serialization, memory safety                         | Native tests, pybind tests, WASM tests when exposed, consumer suites        |
| Published index or host config        | Missing object, wrong prefix, rollback failure                                         | Index contract tests, dry run, remote publication check                     |
| Runtime player mesh                   | Cache poisoning/staleness, worker exhaustion, wearable incompatibility                 | Export adapter tests, API/resource tests, version bump, packaged smoke test |
| Python/Node/Bazel/compiler dependency | Process startup, native ABI, generated diff, numerical or image output drift           | Full matrix and representative byte comparisons                             |

## Safe DSL and materializer rollout

For an additive operation:

1. Add the type or function definition under `src/galois/py/assets/defs`.
2. Add its Python materializer and final-result serializer if applicable.
3. Run `./b ts-deps build` and inspect generated API changes.
4. Add TypeScript transport and Python materialization tests.
5. Run a representative export in both incremental and non-incremental modes.
6. Deploy the Node code, Python code, generated API, and packaged runtime together.

Renaming a materializer kind is equivalent to changing an instruction-set opcode. Prefer adding the new kind, migrating recipes, and removing the old kind only after no packaged tool or mixed-version process can send it.

## Safe binary-format rollout

For a block, flora, shape, group, terrain, or tensor encoding change:

1. Add a reader that accepts the old and new form when rolling compatibility is required.
2. Pin round-trip fixtures from representative existing assets.
3. Test C++, pybind, and WebAssembly readers as applicable.
4. Generate candidate assets and compare dimensions, counts, bounds, and semantic samples—not only file size.
5. Deploy compatible readers before publishing only-new-format assets.
6. Retain old assets and reader support until rollback and cached-client windows close.

If dual reading is impossible, version the logical asset path or coordinate an atomic deployment that prevents old consumers from seeing new bytes.

## Safe static publication rollout

1. Run focused unit and native tests.
2. Run `./b galois assets publish --dryRun` with an affected filter.
3. Review generated definitions and the `asset_versions.json` diff.
4. Publish new content-addressed objects.
5. Run `check-assets-published` and verify every new destination exists.
6. Deploy the updated index and code references.
7. Observe asset 404s, decode errors, client rendering failures, and download volume.
8. Roll back by restoring the previous index/code; old hashed objects must still be available.

Never hand-edit a hash to match bytes that were not produced and uploaded by the exporter.

## Safe runtime player-mesh rollout

1. Build representative combinations: no optional wearables, every slot, hats with hair variants, uploaded VOX binaries, legacy `galoisPath` wearables, and each palette family.
2. Confirm skeleton, animation names, attachment transforms, materials, and GLB MIME/body conversion.
3. Bump `ASSET_EXPORTS_SERVER_VERSION` when output semantics change.
4. Run API cache/resource-limit tests and a container/package smoke build.
5. Deploy with enough worker capacity and monitor build latency, queue depth, worker exits, error results, and memory.
6. Keep the previous deployment and static dependencies available for rollback.

## Toolchain upgrade matrix

For Python, Node, TypeScript, NumPy, Pillow, pygltflib, pybind11, Bazel, compiler, or Voxeloo upgrades:

1. Run the existing tests unchanged before updating expected values.
2. Regenerate the TypeScript DSL and inspect the complete diff.
3. Run Galois TypeScript and Python suites.
4. Run `bazel test //voxeloo/galois/...` and `//voxeloo/py_ext:galois_bindings_test`.
5. Run relevant WebAssembly, API, editor/viewer, and packaging tests.
6. Export a representative matrix covering PNG, GLB/GLTF, audio, definitions, indexes, tensors, and player wearables.
7. Compare output bytes and semantic properties across the old and candidate toolchains.
8. Exercise malformed input and exception translation.
9. Test repeated builds for leaks, worker stability, and deterministic output.
10. Document intentional output changes and the required publication/version bump.

## Pre-merge checklist

- DSL generation succeeds with no missing or superfluous materializers.
- TypeScript lint, build, and Galois tests pass.
- Python Galois tests pass with the current Voxeloo extension.
- Native Galois and pybind boundary tests pass when native code or formats changed.
- Clean and incremental builds agree.
- Representative dry-run exports pass.
- Generated definitions and asset-index diffs contain only intended changes.
- Every new indexed object is uploaded before deployment.
- Player-mesh output changes include an asset-export version bump.
- Container or packaged runtimes import dependencies and perform a real materialization.
- Rollback can restore the old index/code while all old hashed assets remain available.
- The architecture, testing, and upgrade documents reflect any new boundary or invariant.

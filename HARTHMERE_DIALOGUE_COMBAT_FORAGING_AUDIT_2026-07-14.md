# Harthmere Audit — NPC Dialogue, Combat/ECS, Foraging — 2026-07-14

**Scope:** (1) NPC dialogue naturalness / uniqueness / lore + location grounding (Road Ahead excluded), (2) the attack/fighting/damage system and its ECS integration, (3) foraging/harvesting.
**Method:** static code review + a corpus analysis pass over all 185 catalog NPCs' dialogue. No code changed — findings only.

---

## 1. NPC Dialogue

### How it actually reaches the player
Three surfaces feed the talk window, in priority order: the **generated-chat LLM** (`src/pages/api/npcs/generated_chat.ts`, per-NPC system prompt from name + creator description + location + quest context), the **snapshot live-NPC lore** dialog (`snapshot_live_npc_bible.ts`, four canned modes), and the **static fallback** (`npc_dialog_fallback.ts`, 4-variant hashed pool). The 185-entry authored corpus in `npc_compendium.ts` (`dialogue.greeting/service/rumor/questOffer/farewell`) is the seed data that also lands in each NPC's `entity_description`, and is what feeds the LLM prompt and shows verbatim when the LLM path is unavailable (embed/offline/Glitch — the common live case).

### The corpus is heavily templated — this is the headline finding
A phrase/skeleton analysis of the 185 authored NPCs:

- **8 lines are byte-for-byte identical across 89 different NPCs each.** The entire quartet "*My work has a place in this town…*" (service), "*People say Harthmere is safe…*" (rumor), "*There is a task tied to my route and my people…*" (questOffer), and "*Go carefully. Roads, records, and rivers all remember more than people think.*" (farewell) is shared verbatim by 89 NPCs. A second template set is shared by 44 more.
- **After name-substitution, 37 skeleton lines cover 183 of 185 NPCs.** Effectively the whole town speaks from ~4 scripts with the name swapped in.
- **235 distinct 6-word phrases each recur across ≥8 NPCs;** the top ones ("*if you are looking for simple answers…*", "*my work has a place in this town…*") span 89 NPCs.

So: dialogue is **not** unique, and reads as templated rather than human for the large majority of NPCs. The ~30 hand-authored bible characters (Bram Holt, Aldren, Osric Vale, Nessa, Caldus, Thaedryn, etc.) *are* distinctive and lore-grounded — the problem is the long tail generated by `buildNaturalNpcDialogue`/`enrichNpcLoreDialogue`, which emits one of two fixed 5-line blocks.

| # | Severity | Finding |
|---|---|---|
| D-1 | **P1** | 89 NPCs share 4 identical lines; 183/185 collapse to 37 name-swapped skeletons. The enrichment fallback (`npc_lore_dialogue_enrichment.ts::buildNaturalNpcDialogue`) has exactly two hard-coded 5-line templates, so every enriched NPC is a clone. Uniqueness requirement is not met for the tail. |
| D-2 | **P1** | **Dev/scaffolding language is player-visible on 38 NPCs.** Every monster/undead entry ("Thaedryn the Bellbound", the wyrmlings, all `undead_*`) has `greeting: "<Name> has hostile production barks: silence, breath, scrape…"` and `service: "<Name> serves encounter readability: silhouette, threat type, spawn conditions, and loot/state reactions…"`. These are design notes, not dialogue — they'll render verbatim in the fallback path. `harthmereNpcLoreTextIsPlaceholder` does not catch "production barks"/"encounter readability"/"spawn conditions". (Combat NPCs shouldn't open a normal talk window, but the strings are still shipped in `entity_description` and feed the LLM prompt.) |
| D-3 | P2 | **Location grounding is generic, not specific.** 143/185 lines "ground" only by containing the word "Harthmere"; almost none name the NPC's actual district/home/workplace (Old Bridge, Guard Yard, Copper Kettle, the docks). The runtime *does* have a good per-location context object (`location_voice_context.ts` — 5 zones with story text, fed to the LLM via `playerVoiceContextForNpcChat`), but the authored corpus itself rarely mentions where the NPC stands. So grounding depends entirely on the LLM path being live; in the fallback/offline path the lines are location-agnostic. |
| D-4 | P2 | **Backstory echo is weak for the templated tail.** 135/185 NPCs echo ≥2 content words from their own `bibleBackstory` in dialogue — but for the enriched tail that overlap is incidental (shared template words like "route/town/road"), not a real reference to their specific secret or history. The rich bible characters pass genuinely; the generated ones do not. |
| D-5 | P3 | The static fallback pool (`harthmereFallbackNpcDialogText`) is only 4 variants chosen by a name hash, so nearby NPCs on the fallback path frequently repeat each other. Fine as a last resort, but compounds D-1 when the LLM is unavailable. |

**Bottom line:** the *system* (LLM prompt with location + quest + player context, likeability, voice delivery) is well-built and the marquee bible NPCs are strong. The *data* fails the "unique, non-repetitive, human, lore/location-grounded" bar for the ~150 NPCs produced by the two-template enrichment, and 38 NPCs leak design-note text. This is a content-generation problem (regenerate the tail with per-NPC variety + a placeholder filter that catches "production barks/encounter readability"), not a wiring problem.

## 2. Combat / Fighting / Damage + ECS integration

### Architecture (confirmed healthy)
Damage is **fully server-authoritative**: `reduceHarthmereCombatAction` / `computeHarthmereAbilityDamage` compute damage from the ability catalogue + class + level with deterministic, replay-safe variance seeded from the requestId hash — the client's `localFinalDamage` claim is stored for reconciliation display only, never applied (`live_mode_backend.ts` `request_attack`). All the ability preconditions (known/equipped/class/spec/level/weapon/talent/resource/cooldown/zone/PvP/range/LoS) are validated server-side. Server line-of-sight is now a real voxel raycast (48-block cap, injectable sampler registered from `renderers.ts`) — the old always-true stub is gone. NPC melee has a hard 8-unit range cap so the "killed from 34 units away" class of bug is closed. Muck aggression respects safe zones, robot-protected areas, spawn protection, and passive-wildlife rules.

The ECS seam is deliberate and correct: Harthmere live creatures are damaged by the **live-mode reducer**, and the ECS `npcHealth` handler explicitly **returns early** for `isHarthmereLiveModeManagedCombatEntity(event.id)` so the two authorities don't both apply damage (`server/logic/events/handlers/npc.ts:42`). The crosshair targeting (screen-projection pick with a world-reach gate) is the right fix for "creatures are renderer meshes, not ECS entities."

### Findings
| # | Severity | Finding |
|---|---|---|
| C-1 | **P1** | **Attacking a target with no server snapshot is a silent no-op.** `request_attack` requires `next.combat.entitySnapshots[targetId]`; if absent it pushes `combat_rejected:target_state_not_authoritative` and returns — with **no player-facing feedback**. The crosshair registry marks **every** rendered actor `attackable: true` (`harthmere_assets.ts:13108`), including static town-human actors and static-life fallback actors whose published target ids do **not** resolve to a seeded combat snapshot (only muck seeds, livestock seeds, and the Q12 boss are seeded). Result: swinging at a town NPC or a fallback-rendered creature plays the swing animation and does nothing, indistinguishable from a miss. This is the modern residue of the original "attacks don't land" report — narrowed to unsnapshotted actors. |
| C-2 | P1 | **NPC-attack line-of-sight is client-trusted.** The player-attack path (`applyLiveEntityAiPlayerAttack` → `liveEntityAiLineOfSightToPlayer`) decides LoS purely from the client-supplied `lineOfSight` payload string (`:7527`), not the server voxel raycast that `serverCheckLineOfSight` now provides. So a client can suppress incoming NPC damage by claiming `lineOfSight:"false"`, or (less maliciously) terrain between NPC and player is ignored for *incoming* hits even though it's enforced for the player's *outgoing* hits. Asymmetric and spoofable. |
| C-3 | P2 | **Two overlapping NPC-damage clamps, one of them stale-prone.** Incoming NPC damage clamps `attackRange` to `min(snapshot.attackRange, 8)`; the snapshot's `attackRange` can be seeded from aggro/leash values elsewhere, and the hard cap is the only thing saving it. It works, but the design leans on a magic constant rather than a single validated reach — worth consolidating so a future snapshot change can't reopen the ranged-kill bug. |
| C-4 | P2 | **`buildActorSnapshot` hard-codes the player's weapon as a sword** (`mainHandWeaponType: "sword"`, off-hand "none", `:7340`). Any ability with a non-sword `requiredWeaponType` (bow/staff/etc.) either always passes or always fails the `weapon_requirement_not_met` check regardless of what the player actually holds — weapon-type gating is effectively bypassed for the live-mode player. |
| C-5 | P2 | **Crosshair "attackable" ignores zone/hostility.** The pick function filters only on `attackable === false`; town humans in safe zones are attackable candidates. The server correctly refuses (safe-zone / not-hostile / no-snapshot), but the *client* still selects them and shows a swing, so the safe-zone protection reads as "my attacks randomly whiff in town." Pairs with C-1. |
| C-6 | P3 | **4% miss + 65% stray-hit is undocumented to the player and deterministic per requestId.** Functionally fine and replay-safe, but a retried attack (same requestId on idempotent replay) always reproduces the same miss — a client that regenerates the requestId on retry re-rolls it. Minor fairness/consistency note, not a bug. |

**Bottom line:** the damage math and the ECS de-duplication are solid and server-authoritative. The real gaps are at the *targeting seam*: everything the renderer draws is flagged attackable, but only seeded entities can actually be hit, and the mismatch surfaces as silent no-op swings (C-1/C-5). Incoming-damage LoS is the one place client trust leaked back in (C-2), and player weapon-type is stubbed (C-4).

## 3. Foraging / Harvesting

### Pipeline
Live-mode `request_farming_action` routes `gather_seed`, `forage_food`, `hunt_animal`, and `native_plant_harvest` (plus plant/water/harvest/cook/eat/livestock). The pure authority functions live in `mmo_farming_food_stamina.ts`; native plant harvest is handled inline in the backend with its own claim key. Native harvest also fires the ECS `HarvestPlantEvent`, and the gaia plant-growth ticker destroys the ripe plant and drops its container yield as a world drop.

### Findings
| # | Severity | Finding |
|---|---|---|
| F-A | **P1** | **Foraged food spawns and hunted animals never respawn.** `forageHarthmereFoodSpawn`/`huntHarthmereAnimalForFood` compute a `respawnAtMs = nowMs + 12h`, but the backend only persists `next.combat.lootClaims[spawnId] = nowMs` and reads depletion back as `depletedAtMs: lootClaims[spawnId]` — any non-zero timestamp reads as "depleted forever." **Nothing ever expires that claim.** Contrast the exotic-matter path (`liveExoticMatterDepositStateFromClaims`), which correctly checks `replenishesAtMs` and `delete`s the claim when the window passes. So berry bushes and huntable wildlife are one-and-done per player; the authored 12h respawn is dead code. |
| F-B | **P1** | **Native plant harvest double-grants across authorities.** Harvesting a biomes-native farmed plant fires **both**: (1) the ECS `HarvestPlantEvent` → gaia ticker `destroy()` → `newDrop(...)` of the plant's container items into the world (picked up into ECS inventory), **and** (2) the live-mode `native_plant_harvest` op granting `seed.yieldItemId` straight into the live inventory. The two inventories are the standing dual-authority pair (July-13 audit finding 9); here one harvest credits both sides. Depending on which the HUD reads, the player sees either a double count or an ECS-vs-live mismatch. The live-mode side is claim-deduped per plant, but nothing reconciles it against the ECS drop. |
| F-C | P2 | **`gather_seed` has no depletion, cooldown, or source spawn — infinite seeds.** The op validates only that the seed id is real and its `source` list allows the claimed source, then adds 1 seed. There is no world spawn to deplete and no cooldown, so repeatedly submitting `gather_seed` yields unlimited free seeds (and farming XP via the downstream plant/harvest loop). Economy exploit, low blast radius. |
| F-D | P2 | **Carry-weight is enforced inconsistently.** `native_plant_harvest` and (via the shared helper) the gather path check `wouldExceedCarryWeight` before granting, but `forage_food`, `hunt_animal`, and the livestock-product collect path run through `applyLiveFarmingAuthorityResult`, which writes the already-incremented inventory with **no** carry-weight gate. So foraging/hunting can push a player over the carry cap that other actions enforce. |
| F-E | P2 | **Forage/hunt depletion is per-player, not shared-world.** The claim lives on the actor's `lootClaims`, so the same berry bush / animal is independently harvestable by every player and (per F-A) permanently gone for whoever hit it first, with no shared-world state. Combined with F-A this means the wild is a per-account scratch-off card, not a living resource — likely not the intended design. |
| F-F | P3 | **Tree-harvest rejection UX** (already flagged & fixed in the prior pass): server returns `farming_rejected:tree_harvest_not_supported`; the client now surfaces a corrective toast. Confirmed consistent with this audit; no further action. |

**Bottom line:** the crop-plot loop (plant→water→harvest, wither, watered-yield) is correct and well-tested. The **wild-gathering** side has the real problems: permanent depletion with dead respawn timers (F-A), a cross-authority double-grant on native harvest (F-B), an infinite-seed op (F-C), and inconsistent carry-weight enforcement (F-D).

---

## Suggested priority order
1. **F-A** (wild spawns never respawn) and **F-B** (native-harvest double-grant) — both directly corrupt the resource economy players actually touch.
2. **C-1 / C-5** (silent no-op swings on unsnapshotted/safe-zone actors) — the most visible "combat feels broken" residue; either stop marking non-combat actors attackable, or return player-facing feedback.
3. **D-2** (dev language in 38 NPCs' player-visible text) — small, embarrassing, and mechanical to fix (extend the placeholder filter + regenerate those entries).
4. **C-2** (spoofable incoming-damage LoS) — wire the server raycast into the NPC-attack path.
5. **D-1 / D-3 / D-4** (templated, location-thin tail dialogue) — the largest-scope item: regenerate the ~150 enriched NPCs with genuine per-character variety and district references. Content pass, not wiring.
6. **F-C, F-D, C-3, C-4** — economy/consistency hardening.

*No game code was modified in this audit.*

## Fix status — all findings addressed (2026-07-14)

Every finding above has been fixed, unit-tested, and inline-commented (search the codebase for the `(foraging fix …)`, `(combat fix …)`, and `(dialogue fix …)` markers). New tests live in `src/shared/harthmere/test/foraging_economy_fixes.test.ts`, `.../combat_hardening_fixes.test.ts`, `.../dialogue_quality_fixes.test.ts`, and `src/server/gaia/simulations/farming/test/harthmere_harvest_drop_suppression.test.ts`. C-1/C-5 (silent no-op swings) were already resolved in the prior visible-combat-target pass and re-confirmed here.

### Foraging / harvesting

| # | Fix |
|---|-----|
| **F-A** | `forage_food`/`hunt_animal` now read depletion through the respawn-aware `wildSpawnActiveClaimAtMs` helper, which expires a claim once the authored 12h window passes — the bush/animal genuinely respawns instead of being one-and-done forever. Claims are stored under a prefixed `wild_spawn:<id>` key. `src/shared/harthmere/live_mode_backend.ts`. |
| **F-B** | The gaia growth ticker now yields to live mode: in the Harthmere deployment it suppresses the ECS container yield-drop (and clears the container) so the live-mode `native_plant_harvest` op is the single grant — no more double-credit. Gated by a pure, deployment-scoped helper (`harthmereLiveModeFarmingGrantIsAuthoritative`, keyed on `GLITCH_RUNTIME` with an explicit override); plain biomes worlds are unaffected. New module `harthmere_live_mode_farming_authority.ts` + `plant_growth_ticker.ts`. |
| **F-C** | `gather_seed` now enforces a per-`(source, seed)` cooldown (`gatherSeedOnCooldownAtMs`, 5 min) — the infinite-seed exploit is closed while normal foraging is never blocked. |
| **F-D** | `forage_food`, `hunt_animal`, and `collect_livestock_product` now gate their grant on `wouldExceedCarryWeight` before writing, matching the cap the vendor/loot/native-harvest paths already enforce. A weight-blocked forage no longer (wrongly) depletes the spawn. |
| **F-E** | Wild-spawn depletion is projected into the shared world state (`wildSpawnClaims`) and merged back on every actor's sync, so a foraged bush reads as depleted for **all** players until it respawns — no longer a per-account scratch-off. |

### Combat / ECS

| # | Fix |
|---|-----|
| **C-1 / C-5** | Already resolved by the visible-combat-target pass (only combat-family actors are marked attackable; the crosshair no longer flags town humans / unsnapshotted actors). Re-confirmed. |
| **C-2** | Incoming NPC-attack line of sight now uses the **server voxel raycast** (`harthmereServerCheckLineOfSight`, exported from `mmo_combat_authority.ts`) between the NPC and player positions — the same authority outgoing attacks use — instead of trusting the spoofable client `lineOfSight` payload. Falls back to the old hint only when a position is unavailable. |
| **C-3** | The NPC melee reach is now a single exported ceiling + helper (`HARTHMERE_MAX_NPC_ATTACK_RANGE_UNITS` / `harthmereValidatedLiveEntityAttackReach`) instead of a buried magic constant, so a stale/aggro-seeded `attackRange` can never reopen the ranged-kill bug. |
| **C-4** | `buildActorSnapshot` derives the real `mainHandWeaponType`/`offHandWeaponType` from the player's equipment (`harthmere_equipped_weapon_type.ts`, catalogue subtype + name fallback) instead of hard-coding "sword"; empty hands correctly read "unarmed". Every current live-mode ability is `requiredWeaponType: "any"`, so nothing breaks today and future weapon-gated abilities now gate correctly. |
